# Discord Activity Bot

Реализация **всех пяти этапов** из раздела 9 брифа: трекинг голосовой и
текстовой активности, посуточная агрегация, лидерборды за день/неделю/месяц/всё
время, слэш-команды, сводка по серверу, трекинг игр через Rich Presence,
карточка профиля изображением, автосводки в канал, экспорт данных, opt-out и
админ-команды.

Стек — Python 3.12+ / `discord.py` 2.x / SQLite (раздел 4 брифа).

### Про `self_stream`

Формально это этап v3, но флаг `self_stream` приходит тем же событием
`voice_state_update`, что и вход в канал, а колонка `stream_seconds` уже
предусмотрена схемой из раздела 5. Учёт стоил нескольких строк, поэтому включён
сразу — колонка не остаётся вечно нулевой. Rich Presence (игры) не трогали: там
нужен привилегированный intent `GUILD_PRESENCES` и отдельная модель данных.

## Быстрый старт

### 1. Discord Developer Portal

Создайте приложение и бота, затем:

- **Bot → Privileged Gateway Intents** → включите **Message Content Intent**
  (нужен для подсчёта символов и текстовых команд). **Presence Intent** и
  **Server Members Intent** нужны только для трекинга игр — см. раздел про
  Rich Presence ниже.
- **OAuth2 → URL Generator** → scopes `bot` **и `applications.commands`**, права:
  `View Channels`, `Send Messages`, `Embed Links`, `Attach Files`,
  `Read Message History`. Пригласите бота на сервер.

`Attach Files` обязателен: без него `/profile` и `/heatmap` не смогут прислать
картинку, а `/admin export` — файл выгрузки. Права в голосовых каналах не нужны
вообще — бот в войс не заходит, а состояния участников получает через gateway.

Без scope `applications.commands` слэш-команды не зарегистрируются — бот напишет
об этом в лог и продолжит работать на текстовых командах. Чинится повторным
проходом по ссылке-приглашению с добавленным scope, бот при этом с сервера не
слетает.

### 2. Запуск локально

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env   # впишите DISCORD_TOKEN
python -m bot
```

На Windows (PowerShell):

```powershell
python -m venv .venv; .\.venv\Scripts\pip install -r requirements.txt; Copy-Item .env.example .env
```

### 3. Запуск в Docker

```bash
docker compose up -d --build
```

База лежит в каталоге `data/` рядом с проектом — так её легко перенести и
забэкапить обычным `cp`. `stop_grace_period: 30s` даёт боту время корректно
закрыть открытые голосовые сессии по SIGTERM.

Развёртывание на сервере с нуля, перенос накопленной статистики и бэкапы
описаны в [DEPLOY.md](DEPLOY.md).

## Команды

### Слэш-команды

| Команда | Параметры |
|---|---|
| `/leaderboard` | `metric` (голосовые / сообщения / общий рейтинг), `period` (сегодня / неделя / месяц / всё время), `limit` (1–25) |
| `/stats` | `user`, `period` |
| `/profile` | `user` — карточка-изображение |
| `/heatmap` | `user` — тепловая карта; без параметра по всему серверу |
| `/games` | `period`, `limit` — топ игр (нужен трекинг presence) |
| `/serverstats` | `period` |
| `/optout` | отказаться от сбора и удалить свою историю |
| `/optin` | возобновить сбор |

### Админ-команды

Требуют права «Управлять сервером». Discord прячет их от остальных сам, но
проверка продублирована в боте — права на команду можно переопределить в
настройках сервера.

| Команда | Что делает |
|---|---|
| `/admin exclude-channel` | исключить канал из трекинга на лету |
| `/admin include-channel` | вернуть канал в трекинг |
| `/admin exclusions` | показать все действующие исключения |
| `/admin summary-channel` | куда и какие автосводки присылать |
| `/admin reset-stats` | сброс статистики участника или всего сервера |
| `/admin export` | выгрузка в CSV-архив или JSON (по записи на строку) |

Исключения, заданные командой, живут в `guilds.settings_json` и применяются
сразу — перезапуск не нужен. Список из `EXCLUDED_CHANNEL_IDS` действует
одновременно с ними и командами не редактируется.

`/admin reset-stats` требует явного `confirm: True` — действие необратимо.

Все параметры необязательные: без них — общий рейтинг за всё время, топ-10.
Discord сам подсказывает варианты выпадающим списком.

### Текстовые команды

Работают всегда, независимо от слэш-команд — удобны как запасной вариант.

| Команда | Описание |
|---|---|
| `!top` | топ-10 по общему рейтингу за всё время |
| `!top voice week` | топ по времени в войсе за неделю |
| `!top text month 15` | топ-15 по сообщениям за месяц |
| `!stats` / `!stats @user week` | личная статистика и место в рейтинге |
| `!profile` / `!profile @user` | карточка-изображение |
| `!heatmap` / `!heatmap @user` | тепловая карта активности |
| `!games week` | топ игр на сервере |
| `!serverstats month` | сводка по серверу |
| `!help` | список команд |

Порядок аргументов у `!top` — метрика, период, количество. Алиасы команд:
`!leaderboard`, `!лидеры`; `!me`, `!стата`; `!card`, `!профиль`; `!сервер`.
Метрики и периоды понимают
русские названия (`войс`, `текст`, `общий`, `день`, `неделя`, `месяц`, `всё`) и
однобуквенные сокращения (`v`, `t`, `c`, `d`, `w`, `m`, `a`).

Хранилище — SQLite. | Переезд на Postgres при росте: меняется только `db.py`, SQL почти весь переносимый (`ON CONFLICT` есть в обоих). |
| 2 | Хостинг | **Docker-контейнер на VPS** (reg.ru Free Tier). Пошаговое развёртывание — в [DEPLOY.md](DEPLOY.md). | — |

## Как устроен трекинг войса

Ключевая деталь, из-за которой архитектура отличается от наивной «записать
`joined_at`, при выходе посчитать разницу».

**Сегменты.** Отрезок с неизменной парой (канал, `self_stream`) — одна строка в
`voice_sessions`. Любое изменение закрывает текущий сегмент и открывает новый,
поэтому переход между каналами естественно считается сменой сессии (требование
раздела 3.1), а время стрима не нужно вычислять постфактум.

**Инкрементальное начисление.** Фоновая задача раз в `VOICE_FLUSH_INTERVAL`
секунд начисляет прошедшее время в `daily_activity_summary` и двигает
`credited_until`. Отсюда три следствия:

- падение бота теряет максимум один интервал, а не всю многочасовую сессию;
- сессия, пересекающая полночь, автоматически ложится в две дневные записи по
  границе `AGG_TIMEZONE` (это и есть ответ на требование раздела 7 про тайм-зоны);
- при старте открытые сессии закрываются моментом `credited_until` — время
  простоя бота не приписывается пользователям.

**Порог «фантомных» сессий.** Пока сессия короче `MIN_SESSION_SECONDS`, не
начисляется ничего. Если она закрылась раньше порога, строка удаляется бесследно
— без откатов уже записанных агрегатов.

**Синхронизация при старте.** На `on_ready` бот закрывает осиротевшие сессии и
заново открывает их для всех, кто сейчас находится в голосовых каналах, — иначе
после рестарта участники «пропадали» бы до следующего переподключения.

## Трекинг игр (Rich Presence)

**Выключен по умолчанию.** Включение требует двух привилегированных intents, и
если активировать настройку, не включив их в Developer Portal, бот вообще не
войдёт — поэтому дефолт безопасный.

Чтобы включить:

1. Developer Portal → Bot → Privileged Gateway Intents → включить **Presence
   Intent** и **Server Members Intent**.
2. В `.env`: `ENABLE_PRESENCE_TRACKING=true`.
3. Перезапустить бота. В логе появится «Синхронизировано активных
   presence-сессий: N».

Server Members нужен не для самих активностей, а для кэша участников: без него
при старте бот видит только тех, кто уже попадался ему в войсе или сообщениях,
и досчитывает остальных лишь по мере их активности.

### Ограничения платформы

Раздел 3.3 брифа требует обозначать это в интерфейсе, поэтому `/games` пишет
оговорку в подписи эмбеда:

- Игры **не видны** у тех, кто отключил «Отображать текущую активность» в
  настройках приватности Discord. Это решение пользователя, обойти его нельзя —
  и это не баг бота.
- При 100+ серверах бот должен пройти верификацию Discord, иначе привилегированные
  intents перестанут работать.

По умолчанию считается только тип `Playing` — как рекомендует бриф. `Streaming`
здесь означает трансляцию на Twitch/YouTube через интеграцию и к «стриму в войсе»
отношения не имеет: демонстрация экрана приходит через `self_stream` в voice state
и учитывается отдельно, независимо от presence.

## Автосводки

Настраиваются командой, а не переменными окружения — канал у каждого сервера свой:

```
/admin summary-channel channel:#статистика weekly:True monthly:True
```

Сводка всегда за **завершённый** период: в понедельник приходит итог прошлой
недели, первого числа — итог прошлого месяца. Внутри — часы в войсе, сообщения,
активные участники, топ-5 по рейтингу и топ-3 игр, если включён presence.

Отдельного cron не заводится: бот и так работает постоянно, поэтому раз в десять
минут проверяется, не закрылся ли очередной период. Отметка о последней
отправленной сводке лежит в настройках гильдии — благодаря ей перезапуск бота не
приводит ни к повтору, ни к пропуску. Если бот был выключен в момент смены
периода, сводка придёт при следующем запуске.

Пустые периоды не отправляются: если за неделю никто не был активен, сообщения
не будет.

## Данные и приватность

Собирается (раздел 7 брифа):

- метаданные голосовых сессий: кто, в каком канале, когда, сколько, был ли стрим;
- посуточные счётчики сообщений: сколько сообщений и примерно сколько символов, по каналам.

**Содержимое сообщений не хранится и не логируется** — только длина. Боты не
учитываются. Команды самого бота не считаются активностью.

**`/optout`** останавливает сбор и **удаляет всю накопленную историю** участника
на этом сервере: агрегаты, сырые сессии, игры. Открытые голосовые и игровые
сессии закрываются сразу, чтобы фоновая задача не дописала время в уже
очищенные таблицы. Восстановить историю нельзя — `/optin` возобновляет сбор с
момента вызова.

Отказ действует **в пределах одного сервера**: бот многосерверный, и отказ на
одном не должен молча распространяться на другие.

Единственное, что переживает `/optout` — вклад участника в серверную тепловую
карту `activity_heatmap`. Она не хранит идентификаторов: это анонимная сумма по
всему серверу, из которой нельзя вычесть конкретного человека, не пересчитывая
её заново. Личная карта в `user_heatmap` удаляется полностью.

`/admin reset-stats` без указания участника чистит статистику всего сервера, но
сохраняет настройки и список отказов — иначе сброс молча вернул бы в трекинг
тех, кто из него вышел.

## Разработка

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest
```

На Windows прогон нужно уводить в каталог проекта:

```powershell
.venv\Scripts\python.exe -m pytest --basetemp=.pytest_tmp
```

Иначе pytest пытается обновить симлинк `pytest-current` в системном `%TEMP%`,
на что у обычной учётной записи нет прав, и весь прогон падает с `WinError 5`.
Каталог `.pytest_tmp/` игнорируется гитом.

CI гоняет тесты на Python 3.12, 3.13 и 3.14. Нижняя граница — не прихоть:
на 3.12 бот и работает, её же ставит `python:3.12-slim` в [Dockerfile](Dockerfile).
Верхняя закрывает версию, которая стоит на машине разработчика, чтобы
расхождение между «у меня локально зелено» и продом всплывало в PR, а не на
сервере.

199 тестов покрывают нарезку интервалов по часам и суткам (переход через полночь,
не-UTC тайм-зона, переход на летнее время, сохранение суммы), инкрементальное
начисление без задвоения, восстановление после падения, отсечение фантомных
сессий, агрегацию сообщений, фильтрацию по периодам в лидербордах и рейтинге,
сводку по серверу, топ каналов, тепловую карту, трекинг игр и выбор релевантной

### Структура

```
bot/
  main.py              сборка бота, синхронизация команд, корректное завершение
  config.py            конфигурация из окружения
  db.py                весь доступ к SQLite + аналитические запросы
  settings.py          настройки гильдий и отказы от трекинга с кэшем
  schema.sql           схема (раздел 5 брифа + два агрегата, см. ниже)
  timeutil.py          тайм-зона агрегации, нарезка интервалов по часам и суткам
  filters.py           правила исключения каналов
  stats.py             сборка эмбедов — общий слой для обоих видов команд
  cogs/
    voice.py           трекинг голосовой активности
    text.py            трекинг текстовой активности
    presence.py        трекинг игр через Rich Presence
    leaderboard.py     текстовые команды
    slash.py           слэш-команды
    admin.py           opt-out и админ-команды
    summaries.py       автосводки за неделю и месяц
  card.py              рендер карточки профиля на Pillow
  heatmap.py           рендер тепловой карты 7×24
tests/
tools/                 генераторы айдентики и замер запросов
assets/                готовая айдентика
```

Текстовые и слэш-команды — тонкие обёртки над `StatsService`, поэтому
`!top voice week` и `/leaderboard` дают идентичный ответ.

### Замер запросов

Сводка по серверу и топ каналов читают всю таблицу событий гильдии, поэтому
их стоимость растёт вместе с историей. Проверить, во что это обходится на
нужном объёме, можно синтетической базой:

```bash
python -m tools.bench_queries --users 200 --days 365 --channels 5
```

Скрипт заливает выдуманный сервер и печатает время каждого запроса. Ориентир —
лимит Discord на ответ, 3000 мс.

При первом открытии базы, где уже есть данные, бот собирает статистику
планировщика (`ANALYZE`). Без неё SQLite выбирает индекс по форме запроса и
на выборке по одному участнику ошибается на два порядка. Делается это один
раз; дальше статистику освежает `PRAGMA optimize` при остановке.

Вместе с недостающими индексами это единственная долгая часть запуска, и
происходит она **до** входа в Discord: на базе в пару гигабайт — десятки
секунд, на диске VPS больше. Выкат в это время выглядит зависшим, поэтому
`deploy.sh` ждёт входа пять минут.

### Отличия схемы от раздела 5

- В `voice_sessions` и `presence_sessions` добавлены `is_open` и `credited_until` —
  они обеспечивают инкрементальное начисление и восстановление после перезапуска.
- Добавлена `game_events_daily` — посуточный агрегат по играм. Как и с голосом,
  сырые `presence_sessions` чистятся по ретеншну, а статистика должна оставаться.
- Добавлена `voice_events_daily` — поканальная разбивка голосовой активности.
  В брифе такая разбивка есть только для текста (`message_events_daily`), но без
  неё нельзя показать «самый популярный голосовой канал» из раздела 3.4: сырые
  `voice_sessions` чистятся по ретеншну.
- Добавлена `activity_heatmap` — 168 строк на сервер (день недели × час). Даёт
  «самый активный час» из раздела 3.4 и тепловую карту сервера из раздела 3.2.
- Добавлена `user_heatmap` — то же самое с разбивкой по участникам, для личной
  тепловой карты и «пика активности» на карточке профиля. Ограничена 168
  строками на участника. Сделана отдельной таблицей, а не колонкой в
  `activity_heatmap`: та уже накапливала данные, и смена первичного ключа
  потребовала бы миграции с потерей истории.
- Остальные таблицы соответствуют брифу.

Новые таблицы создаются автоматически при старте (`CREATE TABLE IF NOT EXISTS`),
миграция существующей БД не требуется. Но данные в них копятся только с момента
обновления: за более ранние дни разбивки по каналам и тепловой карты не будет.
